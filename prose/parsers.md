# Parsers

How five Markdown parsers turn text into output, side by side, so markz's speed work starts
from how the others are built rather than from their numbers alone. Each is described by the
same six questions, then the ideas are sorted into what markz has taken, what it could take, and
what it leaves on purpose. The plan that acts on this is step 19 in [`plan.md`](plan.md).

The five are cmark-gfm (with comrak, its Rust port), the reference design and what GitHub
renders with; micromark, the spec-exact state machine and markz's oracle; markdown-exit, the
fastest JavaScript parser here; marked, the regex lexer; and markz.

## The questions

1. **Input.** How the text is read: bytes, character codes, a table of line offsets, or regexes
   on the rest of the string.
2. **Blocks.** How containers (blockquotes, list items) and their continuation lines are found.
3. **Inlines.** How plain text is skipped, and how emphasis and links are paired.
4. **Representation.** What it builds, and what that costs to allocate.
5. **Rendering.** How HTML is written from it.
6. **Where the time goes.**

## cmark-gfm and comrak

The reference implementation's design, which most parsers since are variations on.

- **Input.** Bytes, one line at a time. The line is the unit of the block phase.
- **Blocks.** A tree of open blocks. For each line, every open container is asked in turn
  whether the line continues it (`check_open_blocks`), each consuming its prefix; what's left
  may open new blocks (`open_new_blocks`) and is added as text to the innermost leaf
  (`add_text_to_container`). A block that stops matching is finalized. A paragraph's lines are
  copied into the leaf's content buffer.
- **Inlines.** Only after the whole document is read (`process_inlines`), because a reference
  definition anywhere can turn any `[x]` into a link. Each leaf's content is scanned once: a
  256-entry table of special bytes lets the scanner jump over plain text (`find_special_char`),
  and each special byte dispatches to its construct. Emphasis runs go on a delimiter stack and
  link openers on a bracket stack; `process_emphasis` pairs the runs at the end, with a
  per-kind floor so a failed search isn't repeated. The fiddly scanners (HTML tags, autolinks,
  link destinations) are DFAs generated by re2c, so none of them backtracks.
- **Representation.** A linked tree of nodes: parent, first and last child, siblings. comrak
  allocates them in an arena, one pool freed at once, and keeps its delimiters in a second one.
- **Rendering.** An iterator yields enter and exit events over the tree, and the renderer
  writes on each. No recursion.
- **Where the time goes.** Native code, so not comparable with the JavaScript parsers. comrak's
  wasm builds (`comrak`, `comrak-wasm` on npm) pay to copy each document into wasm memory as
  UTF-8 and the HTML back out, and keep the tree inside, which is why they aren't benchmarked.

The design's point for markz: one pass over lines with a stack of open containers, a lookup
table for plain text, and stacks for delimiters and brackets.

## micromark

A state machine per construct, stepping through one character code at a time. It is the most
exact to the spec and the slowest here, about a tenth of the others' speed.

- **Input.** The source is preprocessed into chunks of character codes, with line endings and
  tabs made into codes of their own.
- **Blocks and inlines.** Four content types, each with its own initializer: document
  (containers), flow (leaf blocks), content (paragraph text before it is split into definitions
  and paragraphs) and text (inlines). A construct is a tokenizer: a set of state functions, each
  taking one code, calling `effects.consume` and returning the next state. At each code the
  constructs registered for it are tried with `attempt`, which checkpoints and rolls back when
  one fails, so several can be tried on the same span.
- **Pairing.** Nothing is paired while scanning. Emphasis is an `attention` token until a
  `resolveAll` pass matches the runs; links resolve at the label end. Nested content is parsed
  afterwards by `subtokenize`, which runs the inner content type over the outer tokens' spans,
  repeatedly until nothing is left.
- **Representation.** A flat list of enter and exit events around tokens, each token an object
  with start and end points (line, column, offset). There is no public tree: mdast is built
  from the events by `mdast-util-from-markdown`.
- **Rendering.** `compile` walks the events with a handler per token type.
- **Where the time goes.** Per character: a function call per state, a token object per span,
  a point object per boundary, and the attempts that are rolled back. The price of exactness
  and of extensions that can hook any character.

## markdown-exit

A TypeScript rewrite of markdown-it, and the one to study for step 19: the fastest here, in the
same language as markz.

- **Input.** Before any rule runs, the source is measured into four number arrays, one entry per
  line: where it begins (`bMarks`), where it ends (`eMarks`), its first non-space (`tShift`) and
  its indent with tabs expanded (`sCount`). Block rules read these, not the text.
- **Blocks.** A chain of rules tried in order at each line. Each rule reads ahead as far as it
  needs and returns the next line. Containers are recursive: the blockquote rule rewrites the
  line marks past its `>` prefixes and calls the block tokenizer again on that range, then
  restores them; list items do the same with their indent.
- **Inlines.** After all blocks, a core rule runs the inline parser on each inline token's
  content, a string with prefixes removed. It too is a rule chain, with `text` first: that rule
  skips every character that isn't one of about twenty terminators (`isTerminatorChar`, a
  `switch` on the code) and appends the run to `state.pending`, one string flushed as one text
  token when anything else is pushed. Emphasis runs become delimiters while scanning; after
  scanning, `balance_pairs` matches them and `emphasis` rewrites the tokens. A link label is
  found by skipping tokens ahead, with a cache of positions so the same span isn't parsed
  twice.
- **Representation.** A flat token stream: open, inline and close tokens with a nesting level,
  each inline token holding its own children.
- **Rendering.** A loop over tokens with a function per token type, concatenating a string.
- **Where the time goes.** Little per character: the line tables are computed once, plain text
  is skipped by a `switch` on numbers, and a paragraph's text is one pending string rather than
  one object per run.

## marked

A regex lexer: at each position it tries each rule's regex against the rest of the string.

- **Input.** The rest of the source, as a string. After a match the lexer cuts the matched text
  off the front (`src.substring(token.raw.length)`), which V8 does as a cheap sliced string.
- **Blocks.** Rules tried in order, each an anchored regex. Containers re-lex their content: a
  blockquote strips its `>`s and lexes the result as blocks again, and a list item lexes its
  own text, so nested content is read once per level.
- **Inlines.** Queued while lexing blocks, then run. Each position tries the inline rules in
  order. For emphasis, a masked copy of the text is made first, with code spans, links and
  punctuation replaced by filler, so the emphasis regexes can't match across them.
- **Representation.** Nested tokens, each with its `raw` text and children.
- **Rendering.** A parser walks the tokens with a renderer method per type.
- **Where the time goes.** In V8's regex engine, which compiles regexes to machine code, so the
  common paths are fast. The costs are regexes that backtrack on some inputs, the masked copy,
  and re-lexing nested content.

## markz

One pass over lines for blocks, the inline pass on each leaf as it closes, and a flat tree of
typed arrays. How it compares is the point of this document, so this section is the longest
to check against [`src/`](../src/README.md).

- **Input.** The source string. The block pass finds each line's end with one sticky regex
  step (`LINE`, in `block.ts`), and each block form is tried only on its own first character.
- **Blocks.** cmark's design: a stack of open containers, each line walking it so each container
  consumes its prefix (`line`), then a fixed order of block starts at the cursor (`start`).
  Rejected forms are recognised in the same place as the forms they imitate and stay text with a
  warning. A paragraph's lines are held as ranges until it closes, since the next line may make
  its last line a table header.
- **Inlines.** Per leaf as it closes, not after the document, because markz has no reference
  links: nothing later can change how a leaf reads. The leaf's lines are joined into one flat
  string, with a table mapping positions back to the source. The scan loop dispatches on the
  character; a run of plain text is taken in one sticky regex step (`PLAIN`). Code, math, expressions, autolinks and escapes are consumed where they start.
  Emphasis runs and brackets are items in a doubly linked list, waiting on a stack by kind; a
  match wraps the items between opener and closer into one node. djot's pairing rule means no
  rule of 3 and no split runs. Failed closer searches are remembered (`noCode`, `noDollars`,
  `found`, `labels`), which is what keeps unclosed openers linear.
- **Representation.** A flat tree in parallel typed arrays (type, start, end, parent, first
  child, next sibling, last child), sized from the source length, with data for the few node
  types that carry it in a side table. Offsets, not copies, wherever the source can be used.
- **Rendering.** `html()` folds the tree with `walk`, enter and exit, as cmark's iterator does.
- **Where the time goes.** Before step 19, about 60% inline and 30% blocks, each about twice
  markdown-exit's cost with about as many items as it has tokens: constant factors, not the
  algorithm. The largest was the joined text, built with `+=` into a rope that V8 walks on every
  character read. After step 19, warmed up, markz parses at markdown-exit's speed and renders
  within about 6% of it (`plan.md`, step 19).

## Side by side

|             | cmark-gfm / comrak          | micromark            | markdown-exit              | marked                 | markz                       |
| ----------- | --------------------------- | -------------------- | -------------------------- | ---------------------- | --------------------------- |
| Reads       | bytes, by line              | character codes      | precomputed line tables    | regexes on the rest    | string, by line             |
| Containers  | stack of open blocks        | document tokenizer   | recursive rules            | re-lexes content       | stack of open blocks        |
| Inlines run | after the document          | by `subtokenize`     | after the document         | after blocks, queued   | per leaf, as it closes      |
| Plain text  | lookup table                | per code             | `switch` on codes          | text regex             | sticky regex per run        |
| Emphasis    | delimiter stack, at the end | resolver over events | delimiters, post-processed | regex on a masked copy | stacks by kind, as it scans |
| Builds      | linked tree (arena)         | event list           | flat token stream          | nested tokens          | flat typed-array tree       |
| Renders     | enter/exit iterator         | handler per event    | function per token         | method per token       | enter/exit fold             |

## Ideas for markz

**Taken already.**

- cmark's single pass over lines with a stack of open containers. It's why markz is faster
  than markdown-exit on blockquotes, lists and tables (step 18), where markdown-exit and marked
  read nested content again.
- Delimiter and bracket stacks, with pairing that doesn't rescan.
- A flat tree with no pointers, closer to comrak's arena than to token objects.
- Remembering failed searches, as markdown-exit's position cache and cmark's per-kind floors
  do.
- A non-recursive enter/exit renderer.

**Tried in step 19.**

- **Skipping plain text in one step.** A lookup table by code, as cmark and markdown-exit do,
  gave +11% over a regex test per character; one sticky regex per run gave a little more, since
  V8 runs it as compiled code, and it is one line. It can't backtrack: it is a character class.
- **A flat string to scan.** The one change that mattered most, and not from any parser here:
  joining with `+=` made a rope, and every character read walked it.
- **Block starts by first character.** markdown-exit's rules each check their marker first;
  markz tried every regex on every line.
- **Less per leaf and per node.** Memo records made on first use, one object shape for items,
  a heading's plain text built only for headings, and `html()` skipping escapes and attributes
  when there are none.
- **Not taken.** A `switch` on codes in the scan loop measured no faster than the chain of
  comparisons, so the chain stays. A pending text string, as markdown-exit keeps, and writing
  into the tree without the item list remain open, now that the gap they were for is closed.

**Left on purpose.**

- **Inlines after the whole document.** cmark and markdown-it wait because of reference
  definitions. markz has none, so a leaf is done when it closes.
- **Regex lexing.** marked's speed comes from regexes that can backtrack; markz holds itself to
  linear time (`test/complexity.test.ts`).
- **A state machine per character.** micromark's exactness is why it's the oracle, and its cost
  per character is why markz isn't built that way.
- **Recursive containers.** Re-reading nested content is the cost markz already avoids.
